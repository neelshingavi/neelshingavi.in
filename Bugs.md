# PICT ACM Learning Platform — Deep Project Audit

I have inspected the repository structure, backend architecture, database schema, authentication, learning progression, reward calculations, streak logic, and the existing security/regression reports.

The application has several good foundations, including database uniqueness constraints, server-side authorization, Zod validation, reward deduplication, and protection against destructive content edits. However, there are important gaps between these individual safeguards and the behaviour of the complete application.

### Security notes

The two Critical findings are conditional on deployment configuration, not evidence that the current production instance is compromised. Nevertheless, they should be treated as release blockers.

The in-memory lock issue also deserves attention: a lock that works perfectly on one Node.js process is not a distributed lock. This matters if the platform scales horizontally or runs multiple replicas.

# Complete consolidated issue list — PASC Bonus

Below is the single consolidated checklist of all distinct issues identified in the audit, with duplicates merged. Each item includes its severity and a short corrective action.

Severity: Critical = security/data-loss/release blocker; High = functional or data-integrity issue; Medium = reliability, consistency or scalability issue; Low = minor improvement.

## All identified issues

1. **[Critical]** **Closed day accidentally reopens:** Editing a closed day's learning window with `closesAt = null` can reopen it. **Fix:** Preserve the previous closed state and explicitly validate reopening.

2. **[High]** **Task order gaps permanently block progression:** The learning API expects the immediately preceding numeric order, while the coding API checks existing lower-order tasks. Deleted or non-contiguous tasks can leave students blocked. **Fix:** Use contiguous server-managed ordering or explicit prerequisite IDs and one shared prerequisite validator.

3. **[High]** **MCQ answer key can be cleared:** An admin can update an existing question with `correctOption` or `correctInteger` set to null. **Fix:** Reject published questions without valid answer keys.

4. **[High]** **Task completion is not consistently transactional:** Progression checks and task-content changes can overlap, producing inconsistent completion states. **Fix:** Centralise progression and completion updates in transactional services.

5. **[High]** **Incomplete test execution:** The backend's default `npm test` executes only a narrow test file, leaving most of the test inventory out of the default run. **Fix:** Add a complete test command and make it mandatory in CI.

6. **[High]** **Registration corrupts student identifiers:** Registration accepts PRN or registration number but saves the submitted identifier into both fields. It also trusts submitted profile information instead of canonical roster information. **Fix:** Match the roster record and use its original PRN, registration number, name, branch and roll number.

7. **[Medium]** **Process-local locks and cooldowns:** Coding locks, verification cooldowns and rate-limit state are maintained in individual Node.js processes. **Fix:** Use Redis or another shared atomic store for multi-instance deployments.

8. **[Medium]** **Historical rewards can become inconsistent:** Editing task/question reward configuration after students have completed work can make historical reports inconsistent with current content. **Fix:** Snapshot reward configuration at completion or maintain immutable reward history.

9. **[High]** **Admin reports exclude MCQ points:** Student profiles and leaderboards include MCQ points, but admin reports, module totals, day reports and CSV exports do not consistently aggregate `McqQuestionProgress.pointsAwarded`. **Fix:** Include MCQ points in every reporting and export aggregation.

10. **[High]** **Overall student search uses missing fields:** `rollNo`, `regNo` and `department` are dropped from generated student-stat objects before search filtering. **Fix:** Preserve these fields in the response mapping.

11. **[High]** **Overall student CSV has missing columns:** The query does not select `rollNo`, `regNo` and `department`, although the export expects them. **Fix:** Select and map every exported field explicitly.

12. **[High]** **Roster import merges separate identifiers:** CSV import treats the supplied identifier as both PRN and registration number. **Fix:** Parse and validate separate identifier columns.

13. **[High]** **Roster editing creates inconsistent records:** Editing a claimed roster entry updates `MemberRoster`, but not its linked `Student`. **Fix:** Update both records transactionally or make claimed identity fields immutable.

14. **[Medium]** **Roster sanitisation modifies actual data:** `sanitizeText()` adds formula protection before storing values, potentially changing legitimate names and other data. **Fix:** Store original validated values and escape spreadsheet formulas only during export.

15. **[Medium]** **Deleted student sessions remain valid:** An issued student JWT can remain valid for up to 30 days even after account deletion. **Fix:** Check account existence/active status in authentication middleware or implement token revocation.

16. **[Medium]** **Case-insensitive handle uniqueness is not database-enforced:** Application checks can be bypassed through concurrent registrations using differently capitalised handles. **Fix:** Store a canonical lowercase handle and enforce a unique database index.

17. **[High]** **Stale external handle verification:** A verification request can finish after the student has changed their handle or verification code and overwrite newer information. **Fix:** Use conditional updates matching the original handle and verification code.

18. **[Medium]** **Reopening a day treats task types differently:** Reading, MCQ and Coding have different reward-recovery behaviour when a day is reopened. **Fix:** Establish one reopening/reward policy and implement it consistently.

19. **[Medium]** **Empty MCQ tasks behave inconsistently:** Zero-question tasks can pass prerequisite completion checks, but students see an empty task with no completion record. **Fix:** Require at least one question before publication or explicitly auto-complete empty tasks.

20. **[Medium]** **MCQ reward displayed incorrectly:** The sidebar uses `Task.points`, while actual MCQ rewards are configured per question. **Fix:** Display the sum of question rewards or remove the unused task-level field.

21. **[Medium]** **Reward ledger lacks task foreign key:** `RewardLedger.taskId` is not protected by a database relationship to `Task`. **Fix:** Add the foreign key with an appropriate restrictive deletion policy.

22. **[High]** **Task editor retains previous form values after creation:** Selecting the newly created task does not reliably initialise its form. Old content can be saved against the new task ID. **Fix:** Reset and populate the editor using the newly created task response.

23. **[High]** **Task editor retains stale values after deletion:** Deleting the selected task changes selection without reliably loading the replacement task's content. **Fix:** Use one central task-selection/form-reset function for creation, deletion and provisioning.

24. **[Medium]** **Student reading content displays raw Markdown:** Admin content is authored in Markdown, but the student interface displays the source instead of rendered content. **Fix:** Use a safe Markdown renderer with raw HTML disabled.

25. **[Medium]** **Countdown does not update closed status:** The countdown can reach zero while the interface still displays `OPEN`. **Fix:** Update day state at expiry and refresh authoritative server state.

26. **[Medium]** **Effective closing time is not displayed consistently:** The backend derives a closing time from `releaseAt + windowHours`, but the frontend relies on `closesAt`. **Fix:** Return and display one effective closing timestamp.

27. **[Medium]** **Day navigation retains stale state:** Previous active task indexes, tasks and notices can remain after switching days. Older requests can overwrite newer data. **Fix:** Reset route-dependent state and cancel obsolete requests.

28. **[Medium]** **Coding verification state survives task switching:** `TaskContent` does not have a task-specific key, so `verifying` state can carry over between tasks. **Fix:** Key the component by task ID and guard against stale callbacks.

29. **[Medium]** **Module page has stale-request issues:** Switching modules can allow an older response to overwrite the latest module. **Fix:** Abort previous requests and reset route-dependent state.

30. **[Medium]** **Admin verification student search can display stale results:** Search requests need consistent response sequencing. **Fix:** Use request IDs or `AbortController`.

31. **[Medium]** **Coding task search can display stale results:** Older search responses can replace the latest results. **Fix:** Apply the same request sequencing used in other search interfaces.

32. **[Medium]** **Roster and student-directory requests are not protected against stale responses:** Rapid search, filtering and pagination can result in outdated records appearing. **Fix:** Cancel or ignore obsolete requests.

33. **[Medium]** **CSV upload size mismatch:** The frontend permits files up to 2 MB, while Express JSON parsing is limited to 600 KB. **Fix:** Align limits or use a dedicated multipart/streaming upload endpoint.

34. **[High]** **Production API URL silently falls back to localhost:** Missing `VITE_API_BASE` can direct production visitors' requests to their own computers. **Fix:** Validate production configuration at build time and remove the production localhost fallback.

35. **[Medium]** **Incorrect Excel sheet detection:** Sheet identification searches the entire CSV text for words such as `email` and `prn`, rather than validating the header row. **Fix:** Match normalised header columns and provide a manual selection fallback.

36. **[Low]** **Blob URL revoked too early:** Immediate object URL revocation can race with browser download handling. **Fix:** Revoke after the download has been initiated safely.

37. **[High]** **Concurrent final MCQ submissions can permanently block completion:** Two final correct answers submitted simultaneously can both fail to observe the other's updated progress, leaving the task incomplete. **Fix:** Serialize per-student/task completion or use suitable transaction isolation and retry logic.

38. **[High]** **Reward-window race condition:** Reading/MCQ rewardability is checked before the reward transaction. A day can close between validation and reward creation. **Fix:** Perform availability checks and reward decisions transactionally.

39. **[High]** **Deleting middle tasks breaks existing progression:** Deleting a task without progress does not necessarily renumber remaining tasks. Existing progress on later tasks can prevent sequence repair. **Fix:** Prevent unsafe deletion or provide an atomic, progress-aware task migration.

40. **[Medium]** **Incorrect module status calculation:** A module can appear `UPCOMING` even though some of its days have already closed. **Fix:** Define module-state transitions explicitly based on all day states.

41. **[Medium]** **Duplicate module order values:** The database does not enforce unique module order values. Concurrent creations can also produce duplicates. **Fix:** Use transactional order allocation, a uniqueness constraint and stable secondary sorting.

42. **[Medium]** **Default example tasks can be published accidentally:** Default provisioning inserts sample MCQ and Coding content without a strong publication safeguard. **Fix:** Keep templates in draft state and require admin review before publication.

43. **[Medium]** **Admin coding override does not consistently validate parent publication:** A coding override can operate on a released day inside an unpublished module. **Fix:** Validate parent module state and audit any intentional administrative exception.

44. **[Medium]** **MCQ attempts can be inflated:** Repeat submissions for already-correct answers can increase attempts; double-click submissions are not sufficiently guarded. **Fix:** Return existing results for completed questions and disable submission while pending.

45. **[Medium]** **Incorrect MCQ attempts lack proper activity timestamps:** Progress records do not provide enough activity history for accurate attempt analytics. **Fix:** Add attempt-event records or appropriate `createdAt`/`updatedAt` tracking.

46. **[Critical — conditional]** **Hard-coded fallback JWT secrets:** Admin and student authentication fall back to development secrets outside exact production mode. A misconfigured staging deployment can accept forgeable tokens. **Fix:** Require strong secrets in every deployed environment and permit fallback only in explicit local development.

47. **[Critical — conditional]** **Development student impersonation endpoint:** `/api/dev/login-as` is disabled only when `NODE_ENV === 'production'`. A staging deployment with dev routes enabled can expose unauthenticated student impersonation. **Fix:** Restrict this endpoint to explicit local development or remove it from deployed builds.

48. **[Medium]** **Role authorization is not consistently applied:** `requireRole()` exists but is not used across admin routes. `ADMIN` and `SUPER_ADMIN` effectively have the same privileges. **Fix:** Apply role checks to sensitive endpoints or remove the misleading distinction.

49. **[High]** **College NAT rate-limiting problem:** Students sharing college Wi-Fi share IP-based rate-limit buckets. One student's activity can throttle other students. **Fix:** Rate-limit authenticated requests by student ID, with IP limits as an additional safeguard.

50. **[Medium]** **Inconsistent rate-limiter mounting:** Admin login limiting is mounted at more than one level, generic student-auth limiting affects additional endpoints, and the registration limiter is unused. **Fix:** Mount individual limiters directly on their intended routes.

51. **[Medium]** **CORS failures return generic server errors:** Rejected origins can flow through the generic Express error handler and appear as HTTP 500. **Fix:** Return structured 403 errors and log rejected origins appropriately.

52. **[Medium]** **Health endpoint does not check database readiness:** `/api/health` can report healthy even when the database is unavailable. Startup and shutdown handling also need improvement. **Fix:** Implement separate liveness/readiness endpoints and graceful Prisma/HTTP shutdown.

53. **[Low]** **Unnecessary GET content-type headers:** API clients set JSON content type on GET requests without bodies, potentially triggering unnecessary cross-origin preflights. **Fix:** Set the header only when sending a JSON body.

54. **[Medium]** **Hardcoded proxy trust setting:** `trust proxy = 1` assumes a fixed reverse-proxy topology. Incorrect deployment configuration can compromise client IP detection. **Fix:** Configure trusted proxies according to actual infrastructure.

55. **[Medium]** **No clearly defined ADMIN/SUPER_ADMIN privilege separation:** The permission model does not adequately express the intended differences between roles. **Fix:** Document the role matrix and enforce it consistently.

56. **[Medium]** **Unbounded module duration:** `durationDays` can accept excessively large positive integers, resulting in large allocations and expensive transactions. **Fix:** Set a validated maximum duration.

57. **[Medium]** **Missing numerical boundaries for rewards and CCA:** Points and CCA hours lack sufficiently explicit application-level maximums and precision validation. **Fix:** Validate point limits, CCA limits and decimal precision before database writes.

58. **[Medium]** **Task order accepts unusual values:** Negative or excessively large order values can complicate progression and sorting. **Fix:** Validate order bounds and manage ordering server-side.

59. **[Medium]** **Registration number uniqueness is not enforced:** `Student.regNo` and `MemberRoster.regNo` are treated as identifiers without adequate independent uniqueness constraints. **Fix:** Establish and enforce the correct uniqueness rules in PostgreSQL.

60. **[High]** **Admin reporting has poor scalability:** Overall reports repeatedly filter full progress/reward collections for every student. Complexity and memory usage grow significantly with participation. **Fix:** Use SQL aggregation, Prisma `groupBy`, indexed maps and pagination.

61. **[Medium]** **Insufficient indexes for reporting queries:** Existing composite indexes beginning with `studentId` may not efficiently support queries filtering only on task/question IDs. **Fix:** Add appropriate indexes and validate them using `EXPLAIN ANALYZE`.

62. **[Medium]** **Limited LeetCode/Codeforces submission scanning:** Verification checks only a bounded number of recent submissions (20 for LeetCode and 200 for Codeforces in the audited implementation). Valid older submissions may be missed. **Fix:** Paginate to the relevant release timestamp and distinguish inconclusive checks from genuine failures.

63. **[Medium]** **Weak external-provider failure handling:** Coding verification depends on third-party platforms and their response formats. Timeouts, rate limits and response changes can cause incorrect or confusing outcomes. **Fix:** Add timeouts, retry/backoff, schema validation and explicit provider error states.

64. **[Medium]** **Verification cache can accumulate indefinitely:** Per-user cooldown/attempt maps can retain entries for users who never make another request. **Fix:** Use TTL-based cleanup or a shared cache with automatic expiration.

65. **[Medium]** **Streak calculation can become expensive:** Full historical task and MCQ progress is read to calculate streaks. **Fix:** Query distinct completion dates and consider correctly invalidated derived streak data.

66. **[High]** **No frontend automated test coverage:** Important stateful components have no adequate automated regression tests. **Fix:** Introduce Vitest and React Testing Library for critical components and user journeys.

67. **[High]** **No complete root-level testing workflow:** The root test script is a failing placeholder and does not orchestrate workspace tests. **Fix:** Implement reliable root scripts for frontend, backend, integration and database checks.

68. **[High]** **No repository-defined GitHub Actions CI:** Build, lint, testing, Prisma validation and migration checks are not enforced automatically. **Fix:** Add CI workflows with mandatory pass/fail gates.

69. **[Medium]** **Missing concurrency regression coverage:** Important scenarios involving simultaneous MCQ submissions, closing windows, reopening and task modification lack adequate tests. **Fix:** Add dedicated concurrency and boundary-condition integration tests.

70. **[Medium]** **Node version incompatibility:** The lockfile includes Firebase packages declaring Node `>=24.12.0`, while the audited runtime is Node `22.16.0`. **Fix:** Standardise and declare the supported Node version across development, CI and deployment.

71. **[Medium]** **Incomplete deployment documentation:** The repository does not adequately establish the complete backend deployment contract for environment variables, migrations, health checks and shutdown. **Fix:** Provide a deployment guide and startup validation.

72. **[Medium]** **No fully reproducible integration-test environment:** PostgreSQL, Firebase and third-party coding platforms make local end-to-end testing difficult to reproduce consistently. **Fix:** Provide an isolated test database, Firebase emulator/test doubles and mocked external providers.

73. **[Low/Medium]** **No automated dependency security audit in CI:** Dependency vulnerabilities can enter through package updates without a repository-defined security gate. **Fix:** Add a dependency scanner and a documented vulnerability-remediation process.
